# CHANGELOG

Версия 1.1.0. Актуализация проекта по результатам ручной настройки и проверки на Wazuh Manager 4.14.10 (single-node, rootless Podman). Проект не переписывался: логика загрузки, нормализации, дедупликации и атомарной публикации CDB, идентификаторы правил и декодеры сохранены.

## Изменённые файлы

| Файл | Что изменено и почему |
| --- | --- |
| `wazuh-ti-updater.py` | Версия 1.0.0 → 1.1.0. Значения по умолчанию для путей (`state_dir`, `log_file`, `auth_key_file`, `allowlist_file`, `--config`) переведены на постоянные тома контейнера: `/var/ossec/wodles/wazuh-ti/...` и `/var/ossec/logs/...`, потому что `/usr/local/sbin`, `/etc/wazuh-ti`, `/var/lib/wazuh-ti` при пересоздании контейнера пропадают. В самотест добавлены 6 проверок защиты Auth-Key (маскирование в обычном и URL-виде, чтение ключа, права 0600, отсутствие файла). Все 47 прежних проверок сохранены (итого 53). Логика загрузки, парсеров, истории, бэкапов и публикации не менялась. |
| `config.ini` | Пути приведены к фактической рабочей конфигурации: `state_dir = /var/ossec/wodles/wazuh-ti/state`, `log_file = /var/ossec/logs/wazuh-ti-updater.log`, `auth_key_file = /var/ossec/wodles/wazuh-ti/abusech.key`, `allowlist_file = /var/ossec/wodles/wazuh-ti/allowlist.txt`. Добавлены пояснения про постоянные тома и ссылка на установку без контейнера. `user_agent` обновлён до 1.1. Настоящего ключа в файле нет. |
| `allowlist.txt` | Обновлён путь в заголовке (`/var/ossec/wodles/wazuh-ti/allowlist.txt`). Содержимое без изменений. |
| `wazuh-ti-updater.service` | Переписан для контейнера: пользовательский юнит хоста, запускающий `podman exec` с `run-updater.sh`. Прежний юнит запускал скрипт из `/usr/local/sbin`, чего в контейнере нет, а systemd внутри контейнера не используется. Прежняя версия перенесена в `contrib/baremetal/wazuh-ti-updater.service`. |
| `wazuh-ti-updater.timer` | Адаптирован под пользовательский таймер systemd rootless Podman (расписание 03:20 с задержкой до 15 минут сохранено), добавлено указание на `loginctl enable-linger`. Прежняя версия перенесена в `contrib/baremetal/wazuh-ti-updater.timer`. |
| `wazuh-ti-updater.cron` | Переписан под crontab пользователя rootless Podman: запуск через `podman exec`, задан `XDG_RUNTIME_DIR`. Прежний `/etc/cron.d` вариант перенесён в `contrib/baremetal/wazuh-ti-updater.cron`. |
| `ossec.conf.snippet.xml` | Приведён в соответствие с рабочим Manager: эталонная секция `<ruleset>` целиком (стандартные каталоги не дублируются, блок TI с `decoder_exclude` для `0155-named_decoders.xml` и пятью списками стоит после `etc/decoders` и `etc/rules`). Варианты приёма логов разделены: Вариант А (`<localfile>` на DNS-агенте) и Вариант Б (прямой syslog на Manager), указано, что выбирается один из них; добавлены требования к формату события BIND и особенности Podman. Временный `localfile` интеграционного теста в файл не включён. |
| `README.md` | Переписан по фактическому состоянию: структура проекта, совместимость с Wazuh 4.14.10, особенности Podman, конфликт со стандартным декодером, полная секция `<ruleset>`, установка командами Fish, постоянные пути, оба варианта получения DNS-логов, три уровня проверки (автономные тесты, `wazuh-logtest`, интеграционная проверка), проверка `alerts.json` и Dashboard с примерами поиска по Rule ID, очистка, результаты интеграционного тестирования, ограничения и непроверенные сценарии. Убраны `systemctl` внутри контейнера и указание копировать образцы `.test` в рабочий каталог списков. Правило 100210 явно не заявлено проверенным. |
| `tests/logtest.sh` | Работает через `podman exec` (или напрямую внутри контейнера) и по умолчанию строит события из реальных доменов текущих списков вместо фиксированных `.test`, которые на боевом Manager не срабатывают. Режим `--fixtures` оставлен для тестового стенда. |
| `tests/send-events.sh` | Переписан для интеграционного теста через временный `localfile` в контейнере: дописывает события по реальным доменам, ждёт, сверяет алерты в `alerts.json` и возвращает код 0 или 1. |

## Новые файлы

| Файл | Назначение |
| --- | --- |
| `run-updater.sh` | Запуск updater внутри контейнера из постоянного каталога: выбирает системный `python3` или встроенный Python Wazuh, передаёт аргументы и код возврата. |
| `tools/patch_ossec_conf.py` | Безопасное добавление недостающих строк TI в существующий `<ruleset>` (без замены всего `ossec.conf`, идемпотентно, с проверкой XML, копией и записью на месте), а также добавление и удаление временного `localfile` интеграционного теста по маркерам. Нужен, чтобы исправление `decoder_exclude` не приходилось делать вручную. |
| `tests/check_project.py` | Автономная проверка проекта: состав архива, отсутствие секретов и временных файлов, XML, декодеры и правила, согласованность имён списков и путей, эмуляция событий против ожиданий, генератор и сверка алертов, скрипт правки `ossec.conf`, самотест updater, README и CHANGELOG. |
| `tests/make-live-events.py` | Генератор событий BIND по реальным доменам текущих списков для каждого правила 100201–100204, 100210, 100211 и контрольных запросов. |
| `tests/show_alerts.py` | Таблица TI-алертов из `alerts.json` и автосверка с ожиданиями генератора (PASS или FAIL). |
| `tests/fixtures/ossec.conf.before` | Синтетический образец `ossec.conf` до установки (структура `<ruleset>` рабочего Manager) для тестов скрипта правки. Не является копией рабочего файла. |
| `tests/fixtures/dns-events.expected.tsv` | Ожидаемые вручную декодер, правило и уровень для каждого события `tests/fixtures/dns-events.log`. |
| `contrib/baremetal/README.txt` | Описание установки без контейнера и классических путей. |
| `CHANGELOG.md` | Этот файл. |

## Не выполнялось (требует проверки на живом окружении)

* Подключение реального DNS-сервера и приём реального DNS-трафика (варианты А и Б).
* Интеграционная проверка правила 100210.
* Применение списков через `wazuh-control reload` внутри контейнера без перезапуска.
* Запуск пользовательского таймера и cron на эталонном хосте, пересоздание контейнера.

Автономные тесты (`tests/check_project.py`, самотест updater) подтверждают согласованность файлов и логику, но не заменяют `wazuh-logtest` и интеграционную проверку на работающем Manager.
